A language model on an $8 microcontroller, 3.8–8.2x faster than the open reference port

We measured where the time goes on an ESP32-S3 and rewrote language-model inference for this chip. On the same board and the same weights our engine produces the same text as esp32-ai, several times faster. Our own models, designed for this chip, write better than theirs at the same speed.

Key observation

Speed is bound by memory, not by compute

To write one token the model has to read all of its weights. The chip has three kinds of memory whose speeds differ almost 10x, and the PIE vector unit computes 21x faster than plain code. Once PIE is in use, the processor mostly waits for data.

That gives the rule behind all of the work: speedup = fewer bytes per token. Bytes per token = bits per weight × fraction of weights read ÷ tokens per weight pass. Each technique below shrinks one of these factors.

Path

What we did, in order

  1. Phase 0

    A speed calculator for the chip

    A per-operation cost model: reads from each memory plus compute. On third-party measurements it was not fitted to, the error is 3–5% (only two check points); on our engine it underestimates time by 10–14%. It let us drop ideas on paper before writing code.

  2. Phase 1

    Board measurements

    Our own benchmark firmware: SRAM, PSRAM and flash speed, PIE kernels, DMA. Findings: PIE is 21x faster than plain C (~13x faster than esp32-ai's kernel); after it the bottleneck is PSRAM (83 MB/s on two cores); the PSRAM bus gives ~90 MB/s in total, so DMA adds no bandwidth.

  3. Phase 2

    Model architecture experiments

    27 models trained on a laptop, every compared variant in two runs (except one repeated 2-bit run). Per-layer embeddings (PLE) make the model smarter for the same bytes read; ReLU lets 79% of neurons be skipped at no cost; training for 4 bits is almost free; 4–6 layers beat 12.

  4. Phase 3

    The engine on the board

    C code shared by PC and board, plus PIE assembly kernels. Three versions: 70 → 98 → 110 tokens/s on our model. Every change was measured on its own; failed ones were reverted and logged.

  5. Comparison

    esp32-ai's model on our engine

    Their published weights, not requantized. Their firmware and our engine on one board, on their own benchmark: 94.1 vs 11.5 ms per token, identical text.

  6. Phase 4

    Several tokens per weight pass

    Speculative decoding does not pay on this chip (negative result). Batching tokens known in advance (the prompt, unambiguous pieces of JSON) gives 1.5–2.8x.

  7. Phase 5

    Our own model, by the recipe

    The cost model, calibrated on the board, predicted the speed of the variants within 1–5%. The best variant (vocabulary 8192, PLE table twice as wide, 8.6M parameters), trained on 70M tokens, reaches 0.63 bits per byte vs 0.86 for esp32-ai's 29M model; our 3.4M model already beats it at almost the same speed.

Engine

Where the time goes, theirs and ours

Time per token by stage, the same esp32-ai model

ms per token by stage, their benchmark (200 tokens). The esp32-ai profile is their own output on our board.
4 bits + PIE

Weights are stored in 4 bits and unpacked by vector instructions. esp32-ai uses 8 bits and plain C: twice the bytes and ~13x more cycles per operation (6.2 vs 0.47).

15% of rows

Two-stage output layer: 256 clusters of tokens, score the clusters first, then compute only the best ones in full. Agrees with the full output layer at 99.4–99.8% of positions; the rows that are read match the full computation bit for bit.

2 cores

Every matrix-vector product is split between the cores; the second core spins waiting for work, so handing it a job costs 83–93 cycles.

SRAM

Engine buffers first, then the most-read weights go to fast internal memory (~210 KB), the rest to PSRAM; the PLE table stays in flash.

48% of FFN

ReLU "gate first": compute the gate, then read the other two matrices only for live neurons. A new kernel on the QACC accumulator for the transposed matrix.

−1 ms

Work outside the matrix products: quantization, GELU by table, cluster selection. Guided by the profile, not guesses, it went from 2.2 to 1.2 ms per token.

1. The fastest LLM inference on ESP32-S3 we know of

On the same weights and the same text: 3.8x with identical computation and 8.2x with the two-stage output layer. We found no other open LLM engine using PIE.

2. Models designed for the chip

Architectures compared at equal bytes read per token and checked on the board. Our 3.4M model writes better than esp32-ai's open 29M model at almost the same speed on our engine (0.73 vs 0.86 bits per byte); the best one reaches 0.63.

3. Server-side techniques tested on an MCU

The ideas come from server and mobile LLM inference: candidate screening for the output layer, ReLU activation sparsity and reading only active rows (LLM in a flash), per-layer embeddings. We did not find them measured on a microcontroller, and show which help here, which hurt, and why.

4. A method you can check

A cost model validated on data it was not fitted to, bit-exact agreement between PC and board, every kernel checked against a C reference, every experiment repeated.

"Not found" means a search of GitHub, Hugging Face, arXiv and patents; it is not proof of absence.

Verification

Why the numbers can be trusted

bit for bit

PC, the board with PIE on two cores, on one core, and in plain C give identical digests of all tokens and all logits in every run.

±0.003

The engine's loss on held-out text differs from PyTorch by at most 0.003. The chosen token matches at 98–99% of positions; differences only at near-ties.

<0.1%

Spread between repeats of the same run. This is not the spread across texts: speed drops 1.6x from the start to the end of the context. All measurements are kept as logs in the repository.

Live demo

Try it yourself

An ESP32-S3-N16R8 board connects to any computer over USB. A page in Chrome or Edge flashes the board and then talks to it directly, nothing to install. You type the start of a story, the board continues it in real time, and the page shows the time of every token.

  1. Connect the board with a cable to the COM (UART) USB port.
  2. Open alikup-ai.github.io/bytes-per-token in Chrome or Edge.
  3. Press a Flash button, wait about a minute, close the flasher and reload the page.
  4. "Connect board" → type the start of an English story → "Write".

All models were trained on children's stories. Two images are offered: our varC model (8.6M, 0.63 bits per byte) and esp32-ai's model on our engine. The serial protocol is in engine/demo/README.md.

Limitations

The models are small (3–29M parameters) and trained on children's stories, 20M tokens per model (70M for the best one), one learning rate for all; the quality comparison with esp32-ai uses text from our distribution (their score on it matches their own); speed depends on context length ("110 tok/s" is positions 13–60; the esp32-ai comparison uses their benchmark, positions 4–203); PSRAM at 120 MHz is experimental; energy per token was not measured, and the second core busy-waits; the Arduino core version for the esp32-ai measurement was 3.3.3 (the authors used 3.3.10).
